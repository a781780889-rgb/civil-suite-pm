# Civil Engineering Suite — القسم الأول والثاني والثالث والرابع

منصة احترافية كاملة (Next.js + قاعدة بيانات SQLite موحّدة) لتصميم عناصر الخرسانة المسلحة،
حصر موادها وحديدها بالتفصيل، وإصدار تقارير PDF جاهزة للطباعة.

هذا التسليم يغطي:
- **القسم الأول بالكامل**: حاسبة الخرسانة (تصميم إنشائي حقيقي لكل عنصر + حصر مواد الخرسانة).
- **القسم الثاني بالكامل**: حاسبة حديد التسليح (تفصيل حديد دقيق - Bar Bending Schedule - لكل
  عنصر، بأطوال تثبيت وتراكب وخطافات حقيقية، ومكتبة أسعار متكاملة).

## التشغيل

```bash
npm install
npm run dev       # وضع التطوير: http://localhost:3000
# أو للإنتاج:
npm run build
npm start
```

يتطلب Node.js ≥ 18.17. عند أول تشغيل يُنشئ التطبيق تلقائياً ملف قاعدة البيانات في
`data/civil-suite.sqlite3` (المجلد يُنشأ تلقائياً، ولا حاجة لأي إعداد يدوي).

## البنية التقنية

| الطبقة | التقنية |
|---|---|
| الواجهة | Next.js 16 (App Router) + React 19 + Tailwind CSS |
| الحساب الهندسي | JavaScript خالص، بدون أي مكتبات تصميم إنشائي جاهزة — كل معادلة مكتوبة ومُشتقة يدوياً |
| قاعدة البيانات | SQLite (عبر better-sqlite3) — قاعدة موحّدة لجميع الحاسبات |
| تصدير PDF | التقاط HTML عبر html2canvas ثم تجميعه بصفحات A4 عبر jsPDF (لضمان عرض عربي RTL سليم دون مشاكل تشكيل الحروف) |
| رمز QR | مكتبة qrcode، يُشفَّر داخله ملخص التقرير |

جرّبت كل حاسبة عبر اختبارات فعلية (يدوية وبرمجية) قبل التسليم، وتم التحقق يدوياً من تطابق
الأرقام الناتجة مع الحساب اليدوي للتأكد من عدم وجود أي قيم وهمية أو تقريبية.

## دليل الحاسبات وأساس كل حساب

### 1) القواعد المنفصلة (S-01-A)
تحديد الأبعاد من مساحة التحمل المطلوبة (P/qa الصافية)، ثم تكرار العمق الفعال حتى تحقيق
**فحصي القص الثاقب الكامل** (المعادلات الثلاث لـ ACI 318 §22.6.5.2 مع βc وαs) **والقص أحادي
الاتجاه**، ثم تصميم الانحناء بطريقة Rn-ρ عند وجه العمود.

### 2) القواعد المشتركة والشريطية (S-01-B)
تدعم عمودين أو أكثر (عمودان، ثلاثة أعمدة، أو شريطية لعدد أكبر) عبر **محرك واحد**: يُحسب طول
القاعدة بحيث يطابق مركزها محصلة الأحمال، ثم يُحل **مخطط القص والعزم فعلياً بالتكامل العددي**
(Statics) بدلاً من معادلة جاهزة — هذا يضمن دقة العزم الموجب (سفلي) والسالب (علوي فوق الأعمدة)
مهما اختلف عدد الأعمدة أو تباعدها.

### 3) القواعد المرتبطة Strap (S-01-C)
عمود حافي مقيّد بحد الملكية + عمود داخلي، مرتبطان بجسر لا يلامس التربة. تُحل اللامركزية
وقوة القص المنقولة عبر الجسر بمعادلة اتزان العزم، ثم تُصمَّم كل قاعدة بشكل منفصل وفق رد
الفعل الفعلي بعد أثر الرافعة.

### 4) اللبشة (S-02)
**الطريقة الجاسئة (Rigid/Conventional Method)**: توزيع ضغط التربة بمعادلة الإجهاد المحوري +
الانحناء ثنائي المحور (P/A ± M·c/I) عند أركان اللبشة، فحص قص ثاقب عند أثقل عمود، وتصميم
شرائح تمثيلية بمعاملات عزم الكمرات المستمرة على التباعد الفعلي المُستخرج من إحداثيات الأعمدة.

### 5) الأعمدة (S-03)
معادلة القدرة المحورية القصوى φPn = ασφ[0.85f'c(Ag−Ast)+fyAst] (ACI 318)، مع فحص نحافة
kLu/r مبسّط.

### 6) الكمرات (S-04)
الوزن الذاتي محسوب فعلياً من الأبعاد (وليس تقديراً)، معاملات عزم ACI للحالات الأربع (بسيط،
كابولي، مستمر، مستمر من طرف واحد)، تصميم Rn-ρ، تصميم كانات القص الكامل (بما فيه حد تصغير
التباعد عند القص المرتفع)، وفحص سماكة الترخيم الدنيا (ACI Table 9.3.1.1).

### 7) البلاطات (S-05)
- **أحادية الاتجاه**: نفس منهجية الكمرات لكن بعرض 1م + حديد انكماش/حرارة.
- **ثنائية الاتجاه**: توزيع الحمل بين الاتجاهين بطريقة **توافق الانفراف** (wx = w·Ly⁴/(Lx⁴+Ly⁴))
  وهي طريقة تحليلية تُشتق حسابياً من الأبعاد مباشرة (بلا جداول معاملات جاهزة عرضة للخطأ)، ثم
  تصميم كل اتجاه بمعاملات العزم المستمر.

### 8) الجدران (S-06)
تسليح أدنى وفق ACI 318 §11.6، مع خيار **جدار استنادي** يُصمَّم كعنصر كابولي رأسي تحت ضغط
تربة حقيقي بنظرية Rankine (Ka = tan²(45°−φ/2))، والعزم والقص مُشتقّان بالتكامل الرياضي للحمل
المثلثي المتزايد.

### 9) السلالم (S-07)
معادلة الراحة 2R+T=630mm لاشتقاق عدد وارتفاع القوائم من الارتفاع الكلي فعلياً، حجم القلبة
والدرجات من الهندسة الفعلية (الطول المائل، المثلثات)، تصميم انحناء كبلاطة مائلة. يدعم مستقيم
وL وU (فَرشتان + بسطة) بالإضافة إلى **دائري/حلزوني** (تصميم كابولي شعاعي من عمود مركزي، بمساحة
قطاع دائري حقيقية = 0.5(Rout²−Rin²)Δθ).

### 10) الخزانات (S-08)
**مستطيلة**: جدار كابولي تحت ضغط هيدروستاتيكي مثلثي (Mu=γwH³/6 مُشتقة بالتكامل).
**دائرية**: نظرية شد الطوق الكلاسيكية T=γw·h·R. يشمل تصميم سقف (بلاطة مستطيلة أو دائرية
بمعادلات الصفائح الدائرية الكلاسيكية)، ومساحات العزل واللياسة.

### 11) المسابح (S-09)
تصميم الجدار على **أسوأ حالتين فعلياً ويُقارن بينهما**: الامتلاء (ضغط ماء للخارج) والفراغ تحت
منسوب الأرض (ضغط تربة Rankine للداخل)، مع فحص رفع (Uplift) عند الفراغ، وحساب تدفق المضخة
المطلوب من حجم المسبح ومدة دورة التنقية.

### 12) حاسبة المواد (متكاملة في كل حاسبة + أداة مستقلة S-10)
طريقة **الحجم الجاف** (معامل 1.54) بالنسب الحجمية القابلة للتخصيص الكامل (رتبة، نسبة خلط،
نوع أسمنت، نسبة هدر، نسبة ماء/أسمنت)، وليست جدول أرقام جاهزة.

## ملاحظات منهجية بالشفافية الكاملة
- منهجية اللبشة والبلاطات ثنائية الاتجاه والخزانات هي طرق مبسّطة معتمدة هندسياً (وليست تحليل
  عناصر محددة FEM) — مناسبة لمعظم الحالات العملية، مع الإشارة صراحة داخل نتائج كل حاسبة إلى
  متى يُنصح بتحليل أدق.
- تصميم برج/أعمدة دعامة الخزان العلوي، واستقرار الجدار الاستنادي الكامل (انزلاق/انقلاب)، خارج
  نطاق هذا التسليم (يُستكملان عبر حاسبتي الأعمدة والكمرات، أو يمكن إضافتهما كوحدة مستقلة لاحقاً).
- تأثيرات الالتواء في العمود المركزي للدرج الدائري غير مُصمَّمة تفصيلياً (يُنصح بمراجعة هندسية إضافية).

# القسم الثاني — حاسبة حديد التسليح (Bar Bending Schedule)

حاسبة تفصيل حديد كاملة ومستقلة عن التصميم الإنشائي: يُدخل المهندس أبعاد العنصر وتوزيع الحديد
المُعتمد (من القسم الأول أو من مخطط تنفيذي جاهز)، فتُخرج الحاسبة **جدول تفصيل حديد كامل**
(نوع كل مجموعة أسياخ، القطر، الطول الفعلي للقطعة الواحدة شاملاً الخطافات، العدد، عدد الأسياخ
التجارية ووصلات التراكب اللازمة، الوزن، والتكلفة)، دون أي معامل تقريبي ثابت.

## المحرك الحسابي المشترك (`lib/calc/rebar/core.js`)
كل الأطوال التالية حقيقية 100%، مُشتقة من القطر ومقاومة الخرسانة وإجهاد الحديد الفعليين وفق
**ACI 318-19 §25** (وليست معاملاً جاهزاً كـ ×1.15):

- **طول التثبيت (Development Length)**: المعادلة العامة الكاملة `ld = fy·ψt·ψe·ψs·ψg / (1.1·λ·√f'c·(cb/db)) × db`
  باستخدام الغطاء/التباعد الفعليين لحساب `cb`، مع `Ktr=0` كتبسيط محافظ مسموح به صراحة في الكود.
- **طول تثبيت الخطاف (Hooked Bar)**: معادلة ACI 318-19 الجديدة `ldh = 0.24·fy·ψe·ψc·ψr/√f'c × db`.
- **طول التراكب**: شد (Class A = 1.0×ld أو Class B = 1.3×ld) وضغط (وفق §25.5.5 بمعامل تصحيح
  عند خرسانة أضعف من 21MPa).
- **هندسة الخطافات (90°/135°/180°)**: طول حقيقي = امتداد مستقيم (12db أو 4db/65مم للحديد
  الرئيسي، 6db/75مم للكانات) **+ طول قوس الانحناء الفعلي** المحسوب من قطر الانحناء القياسي
  (6db/8db/10db حسب حجم السيخ) — وليس رقماً تقريبياً.
- **تقسيم الأسياخ التجارية (12م)**: عند تجاوز الطول المطلوب الطول التجاري، تُحسب أطوال التراكب
  الفعلية وعدد القطع والوصلات اللازمة تلقائياً.
- **وزن المتر الطولي**: من الكثافة الفعلية للفولاذ (7850 kg/m³) مباشرة، وليس من جدول جاهز.

## مكتبة الكانات (`lib/calc/rebar/stirrups.js`)
مستطيلة، مربعة، دائرية، متعددة الأضلاع، ومزدوجة (بأشواط إضافية/Cross-ties) — كل شكل يُحسب على
**محور السيخ الفعلي** (لا تقريب) مع طول الخطاف المطابق للقطر.

## مكتبة الأسعار وقاعدة البيانات
جدول `steel_price_lists` مستقل يخزّن قوائم أسعار متعددة (لكل مشروع أو عامة)، يمكن اختيار أي
منها مباشرة داخل أي حاسبة، وتُطبَّق التكلفة على **الوزن شامل الهدر** (وليس الصافي) بالترتيب:
حديد ← قص ← تشكيل ← تركيب ← نقل ← خصم ← ضريبة.

## ملاحظات شفافية إضافية (القسم الثاني)
- امتداد الحديد داخل المساند (الأعمدة/البسطات) يُفحص فعلياً مقابل طول التثبيت المطلوب؛ إن لم
  يكفِ العرض المتاح، تُضيف الحاسبة خطاف 90° تلقائياً وتوضح ذلك في قسم الملاحظات الهندسية.
- عدد بلوكات الهوردي المذكور استرشادي لأغراض حصر الكميات فقط (بمقاس بلوك طولي نمطي 40 سم)،
  وليس جزءاً من التصميم الإنشائي للبلاطة (ذلك ضمن القسم الأول).
- تأثيرات العزم الالتوائي والانحناء ثنائي المحور للعمود المركزي في السلم الدائري خارج نطاق
  حاسبة تفصيل الحديد (تخص التصميم الإنشائي في القسم الأول).

# القسم الثالث — نظام حصر الكميات (Quantity Takeoff)

## الفكرة المعمارية
بدل كتابة معادلة مستقلة لكل صنف من الأصناف الثمانين تقريباً الموزّعة على 14 تخصصاً (أعمال
ترابية، خرسانة، حديد، مباني، لياسة، عزل، أرضيات، أسقف تشطيب، دهانات، نجارة، ألمنيوم وزجاج،
كهرباء، صحي، طرق)، بُني القسم على سبع دوال هندسية بدائية فقط (`lib/boq/primitives.js`: حجم
صندوقي، حجم أسطواني، حجم طبقة، مساحة ناقص فتحات، طول إجمالي، عدد إجمالي، إدخال يدوي)، وسجل
أصناف (`lib/boq/categoryRegistry.js`) يربط كل صنف بالدالة المناسبة له وحقول إدخاله. هذا يحقق
مبدأ DRY المطلوب صراحة في المواصفة، ويجعل إضافة صنف جديد (بما فيها الأصناف المخصّصة التي
يضيفها المستخدم من الواجهة) مجرد سطر تعريف جديد لا دالة حساب جديدة.

## التكامل الحقيقي مع القسمين الأول والثاني
هذه هي النقطة الأهم في هذا القسم: عناصر الخرسانة وحديد التسليح في حصر الكميات **لا تُعيد
اشتقاق الكمية بمعادلة مبسّطة خاصة بها**. بدلاً من ذلك:
- عنصر حديد تسليح في BOQ يُربط إلزامياً (`rebar_link`) بحساب محفوظ فعلياً في القسم الثاني،
  ويسحب `results.totals.totalWeightKg` منه مباشرة — أي الوزن النهائي شاملاً الوصلات
  والخطافات والكانات كما فصّلته حاسبة BBS الحقيقية، لا تقديراً تقريبياً. البديل الوحيد هو
  إدخال الوزن يدوياً (لا معامل تقريبي بديل - ممنوع صراحة في متطلبات القسم).
- عنصر خرسانة في BOQ يمكن ربطه اختيارياً بحساب محفوظ في القسم الأول ليسحب
  `results.quantities.concreteVolumeM3` الفعلي (المصمَّم وفق ACI 318، لا صندوقاً مبسّطاً)،
  ثم يُشغَّل عليه محرك حصر مواد الخرسانة نفسه من `lib/calc/materials.js` (لا نسخة موازية
  منه) لإنتاج كميات الأسمنت/الرمل/البحص. أو يُدخَل هندسياً مباشرة (طول×عرض×سماكة) للتقدير
  السريع في مراحل مبكرة لا تحتاج تصميماً إنشائياً كاملاً بعد.
- تحقّق من هذا التكامل فعلياً اختبار حيّ (وليس Mock) في `tests/`: إنشاء حساب حديد وحساب عمود
  حقيقيين عبر `/api/calculate`، حفظهما، ثم ربطهما بعنصرَي BOQ والتحقق أن الكمية المسحوبة
  تطابق نتيجة الحاسبة الأصلية تماماً.

## الاستيراد — النطاق الحقيقي لكل صيغة
| الصيغة | الحالة | التفاصيل |
|---|---|---|
| Excel / CSV | ✅ كامل | أعمدة قياسية (نموذج قابل للتنزيل من واجهة الاستيراد)، تحقّق ورفض لكل صف مع السبب |
| DXF | ✅ حقيقي، محدود النطاق | قراءة هندسة فعلية (إحداثيات حقيقية) لعناصر LINE/LWPOLYLINE/CIRCLE، تجميع حسب الطبقة (Layer)، طول فعلي ومساحة فعلية (صيغة Shoelace). **لا** يوجد تصنيف تلقائي لربط اسم الطبقة بصنف BOQ — المستخدم يُعيّن ذلك يدوياً لكل طبقة في واجهة المعاينة، لأن اسم الطبقة وحده لا يكفي هندسياً لتحديد نوع العنصر أو سماكته |
| IFC (BIM) | ✅ حقيقي، محدود النطاق | مُحلِّل نصي كامل لصيغة STEP/SPF (بلا مكتبة خارجية) يستخرج الكيانات الإنشائية المعروفة وأي `IfcElementQuantity` مرتبطة بها فعلياً في الملف. **لا** يوجد محرك تمثيل هندسي ثلاثي الأبعاد (B-rep) لإعادة بناء كميات من الهندسة الخام إن لم يُصدّرها برنامج BIM كمجموعة كميات جاهزة — العنصر بلا مجموعة كميات يُعاد `null` صراحة ويُطلب إدخاله يدوياً، لا تخميناً |
| DWG | ❌ غير مدعوم | صيغة ثنائية مملوكة تتطلب مكتبة تحويل تجارية (لا تتوفر مجاناً)؛ الحل: تصدير DXF من برنامج الرسم (Save As) ثم استيراده |
| PDF | ❌ غير مُفعَّل في هذا الإصدار | استخراج جداول من تخطيطات PDF المتفاوتة غير موثوق بما يكفي لإدراجه دون مراجعة يدوية شبه كاملة لكل حالة؛ استخدم Excel/CSV/DXF/IFC بدلاً منه |

كل مسارات الاستيراد (بما فيها DXF/IFC بعد تعيين الأصناف) تمر بخطوة معاينة `{valid, rejected}`
قبل أي كتابة في قاعدة البيانات، ثم إدراج جماعي داخل معاملة واحدة (`bulkInsertBoqElements`)
يتحقق من التكرار لكل صف، ويُنتج سجل استيراد (`boq_imports`) يوثّق عدد المستورد والمرفوض وسببه.

## الذكاء الاصطناعي (`lib/boq/ai.js`)
مساعد اختياري (يتطلب `ANTHROPIC_API_KEY` في بيئة الخادم — بدونه يُعيد خطأ واضح لا فشلاً صامتاً
ولا نتيجة ملفّقة) يحلّل صورة مخطط عبر Claude Vision. يلتزم حرفياً بقواعد القسم الخامس
الإلزامية: لا يخترع بعداً غير مكتوب على المخطط، يُرفق كل اقتراح بمستوى ثقة (0–1) ومبرر نصي،
ولا يكتب أي شيء في قاعدة البيانات بنفسه — كل اقتراح يمر عبر نفس مسار "إضافة عنصر" اليدوي
العادي بعد مراجعة المستخدم واعتماده صراحةً لكل عنصر على حدة (زر "اعتماد وإضافة" في `/dashboard/boq/ai`).

## الأمان — ما هو حقيقي وما هو خارج نطاق هذا التسليم
- **حماية SQL Injection**: حقيقية وكاملة — كل استعلام في `lib/db.js` عبارة عن Prepared
  Statement بمعاملات مُسمّاة عبر `better-sqlite3`؛ لا يوجد تجميع نصوص SQL يدوي في أي مسار.
- **حماية XSS**: تلقائية من React (لا يوجد `dangerouslySetInnerHTML` في أي مكوّن من مكوّنات
  هذا القسم).
- **المعاملات (Transactions)**: حقيقية — كل عملية إنشاء/تعديل/حذف/استيراد جماعي مُغلَّفة في
  `db.transaction()`، بما يضمن تراجعاً كاملاً عند أي فشل جزئي.
- **سجل التدقيق (Audit Log)**: حقيقي وكامل — كل تعديل يُسجَّل بحالته قبل وبعد في
  `boq_audit_log`، ويُحتفَظ بالسجل حتى بعد حذف العنصر نفسه.
- **الترقيم الصفحي والفهرسة**: حقيقية — فهارس فعلية على `project_id`/`category_key` في
  SQLite، واختبار أداء (وليس مجرد ادّعاء) يُدرج 3000 عنصر ويقيس زمن استعلام صفحة واحدة منها.
- **RBAC (صلاحيات متعددة المستويات) والتشفير**: **غير مُنفَّذين في هذا التسليم** — التطبيق
  الأساسي بأكمله (الأقسام 1 و2 أيضاً) لا يحتوي أي نظام مصادقة (تسجيل دخول) من الأصل، وإضافة
  صلاحيات حقيقية بلا نظام مصادقة يسبقها غير ذي معنى. حقل `actor` النصي الاختياري موجود في
  `boq_audit_log` جاهزاً للربط بنظام مصادقة إن أُضيف لاحقاً، دون الحاجة لإعادة هيكلة.
- لم يخضع أي مما سبق لاختبار اختراق فعلي (Penetration Testing) — "حماية حقيقية من حيث
  البنية" لا تعني "مُدقَّقة أمنياً من طرف مستقل"، والفرق بينهما مهم قبل أي استخدام إنتاجي حسّاس.

# القسم الرابع — نظام إدارة المشاريع (Project Management System)

## الفكرة المعمارية
هذا القسم هو "القلب الرئيسي للنظام" كما وصفته المواصفة، فبُني ليكون الطبقة التي تُظلّل بقية
الأقسام لا طبقة موازية لها:
- **لا جدول `pm_projects` منفصل.** جدول `projects` الموجود أصلاً (والذي تعتمد عليه حاسبات
  القسم الأول وحديد القسم الثاني وعناصر BOQ في القسم الثالث عبر `project_id`) وُسِّع بأعمدة
  جديدة فقط (`ALTER TABLE ADD COLUMN` بفحص `PRAGMA table_info` أولاً، فعّالة التكرار/Idempotent)
  ليحمل كل الحقول الغنية (المالك، المقاول، الاستشاري، مدير المشروع، الإحداثيات، الميزانية،
  الحالة...). هذا يحقق حرفياً ما وثّقه README القسم الثالث سابقاً: "قاعدة البيانات مصمَّمة
  لتكون نواة موحّدة يمكن أن تُبنى عليها إدارة المشاريع الكاملة دون الحاجة لإعادة هيكلة".
- كل الجداول الجديدة (20 جدولاً) ببادئة `pm_` (نفس نمط `boq_*`)، مُعرَّفة ومُهيَّأة بالكامل في
  `lib/pm/schema.js` وحده — **لم يُعدَّل `lib/db.js` بحرف واحد**، صفر تأثير على الأقسام 1-3.
- طبقة الوصول لقاعدة البيانات مقسَّمة إلى 16 وحدة مستقلة تحت `lib/pm/db/` (مشاريع، مراحل،
  مهام، فريق، ميزانية، موارد، مخاطر، جودة، سلامة، مستندات، اجتماعات، تنبيهات، تدقيق، تقارير،
  إحصاءات) بدل ملف واحد ضخم — تطبيق حرفي لقاعدة "Modular Architecture" الإلزامية.

## محرك المسار الحرج (Critical Path Method) — `lib/pm/criticalPath.js`
أهم قطعة منطق حقيقية في هذا القسم: تمريرتان فعليتان (أمامية لحساب ES/EF، خلفية لحساب LS/LF)
تدعمان أنواع التبعية الأربعة القياسية (FS/SS/FF/SF) مع فترات تأخر/تقديم بالأيام، وترتيباً
طوبولوجياً حقيقياً بخوارزمية Kahn يكتشف أي دورة تبعيات (Circular Dependency) ويرفضها بخطأ
واضح بدل نتيجة غير معرَّفة. الطفو الحر (Float) والمسار الحرج يُشتقّان حسابياً من الفرق بين
LS وES لكل مهمة، لا يُقدَّران. مُختبَر بـ10 اختبارات وحدة حقيقية تغطي: سلسلة خطية، مسارات
متوازية بطفو، الأنواع الأربعة، وكشف الدورات (`tests/pm/criticalPath.test.js`).

## التكامل الحقيقي مع الأقسام الثلاثة الأولى
تبويب "نظرة عامة" في كل مشروع يعرض فعلياً (استعلام SQL حي، لا رقماً ثابتاً): عدد الحسابات
الهندسية (`calculations`) المرتبطة بنفس `project_id`، وعدد عناصر حصر الكميات وتكلفتها
الإجمالية من `boq_elements` لنفس المشروع (`lib/pm/db/projectStats.js`). أي حساب خرسانة أو
حديد أو عنصر BOQ يُنشأ لمشروع من هذه الواجهات الثلاث يظهر فوراً هنا، لأنها الجدول نفسه لا نسخة منه.

## الذكاء الاصطناعي (`lib/pm/ai.js`)
نفس نمط `lib/boq/ai.js` تماماً — يتطلب `ANTHROPIC_API_KEY` (خطأ واضح بدونه)، ولا يكتب أي شيء
في قاعدة البيانات بنفسه. أربع قدرات تطبّق البند الثالث عشر الإلزامي حرفياً ("لا يعتمد أي قرار
نهائي بدون موافقة المستخدم"، "يجب توضيح سبب كل توصية"، "استخدام البيانات الفعلية فقط"): تحليل
صحة المشروع (تقدم/تأخير/أسباب/حلول مقترحة) من بيانات المشروع الحقيقية، تلخيص محاضر الاجتماعات،
الإجابة عن استفسارات حرة بالاعتماد حصراً على البيانات المُرسَلة، وفقرة سردية تفسّر أرقام تقرير
محسوب فعلياً دون اختراع أرقام جديدة. كل استجابة JSON منظّمة تحمل حقل `reasoning` يوضح الأساس.

## الصلاحيات (`lib/pm/roles.js`) — ما هو حقيقي بالضبط
مصفوفة صلاحيات كاملة لـ14 دوراً × 12 وحدة × 4 إجراءات (عرض/تعديل/حذف/اعتماد)، **مُنفَّذة
ومُفعَّلة فعلياً**: كل مسار API في `/api/pm/*` يستقبل `actor_role` صراحةً ويرفض الطلب (403
حقيقي) إن لم يملك الدور صلاحية الإجراء — وليست مجرد واجهة تعرض/تخفي أزراراً شكلياً. الفجوة
الوحيدة، بشفافية كاملة: التطبيق بأكمله (الأقسام 1-3 أيضاً) **لا يحتوي نظام مصادقة/تسجيل دخول
من الأصل**، فـ"الدور الحالي" في الواجهة (`ActorBar`) اختيار من المتصفح محفوظ محلياً، وليس
هوية مُتحقَّق منها بجلسة آمنة. حقلا `actor`/`actor_role` جاهزان تماماً للربط بنظام مصادقة
حقيقي لاحقاً دون أي تغيير في منطق المصفوفة نفسه.

## الأمان — ما هو حقيقي وما هو خارج نطاق هذا التسليم
- **SQL Injection / XSS / المعاملات / سجل التدقيق / الترقيم الصفحي والفهرسة**: حقيقية وكاملة،
  بنفس الأساس الذي وثّقه القسم الثالث أعلاه حرفياً — Prepared Statements في كل استعلام،
  React بلا `dangerouslySetInnerHTML`، `db.transaction()` لكل عملية مركّبة، فهارس فعلية على
  كل عمود `project_id` ومعظم أعمدة التاريخ/الحالة.
- **الصلاحيات (RBAC)**: حقيقية وفعّالة كما فُصِّل أعلاه، بفجوة واحدة موثّقة (لا مصادقة).
- **CSRF**: غير مُعالَج بتوكن مخصّص في هذا التسليم — نفس وضع الأقسام 1-3 سابقاً.
- **المصادقة الثنائية (2FA) والتشفير عند الراحة (Encryption at Rest)**: **غير منفَّذين** —
  يتطلبان نظام مستخدمين/جلسات حقيقياً كأساس أول، وهو غير موجود بعد في التطبيق كما وثّقنا.
- **تخزين المستندات**: حقيقي على قرص الخادم المحلي (`data/pm-uploads/`) لا تخزيناً سحابياً/CDN؛
  يحتاج نسخاً احتياطياً لهذا المجلد ولملف SQLite معاً في أي بيئة إنتاج فعلية.
- **الإشعارات (بريد/SMS)**: التنبيهات مُخزَّنة وحقيقية داخل التطبيق، لكن لا يوجد إرسال فعلي
  خارج التطبيق (يتطلب مزوّد بريد/SMS وعامل خلفي دائم غير متوفرين في هذا الـ stack).
- لم يخضع أي مما سبق لاختبار اختراق فعلي، تماماً كتنويه القسم الثالث.

## التوسّع لاحقاً
مع اكتمال القسم الرابع، تحوّل جدول `projects` فعلياً إلى النواة الموحّدة التي وُعِد بها —
كل قسم مستقبلي (نظام مصادقة حقيقي يُفعِّل RBAC بالكامل، تكامل بريد/SMS فعلي للتنبيهات، تخزين
سحابي للمستندات) يُضاف بنفس نمط `lib/pm/` (وحدة مستقلة تحت `lib/`، بادئة جداول خاصة بها،
صفر تعديل على `lib/db.js`) دون الحاجة لإعادة هيكلة أي شيء مما سبق.
