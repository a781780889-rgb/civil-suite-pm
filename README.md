# Civil Engineering Suite — القسم الأول والثاني والثالث والرابع والخامس والسادس والسابع

منصة احترافية كاملة (Next.js + قاعدة بيانات SQLite موحّدة) لتصميم عناصر الخرسانة المسلحة،
حصر موادها وحديدها بالتفصيل، وإصدار تقارير PDF جاهزة للطباعة.

هذا التسليم يغطي:
- **القسم الأول بالكامل**: حاسبة الخرسانة (تصميم إنشائي حقيقي لكل عنصر + حصر مواد الخرسانة).
- **القسم الثاني بالكامل**: حاسبة حديد التسليح (تفصيل حديد دقيق - Bar Bending Schedule - لكل
  عنصر، بأطوال تثبيت وتراكب وخطافات حقيقية، ومكتبة أسعار متكاملة).
- **القسم السابع بالكامل**: نظام إدارة المعدات (دورة حياة كاملة: تسجيل → تخصيص → حجز → تشغيل →
  وقود → صيانة → أعطال → قطع غيار → نقل → تكلفة مرتبطة بالميزانية الفعلية → تقارير)، تفاصيله في
  قسم "القسم السابع — نظام إدارة المعدات" أسفل هذه الوثيقة.

## التشغيل

```bash
npm install
npm run dev       # وضع التطوير: http://localhost:3000
# أو للإنتاج:
npm run build
npm start
```

يتطلب Node.js ≥ 18.17. عند أول تشغيل يُنشئ التطبيق تلقائياً ملف قاعدة البيانات في
`data/civil-suite.sqlite3` (المجلد يُنشأ تلقائياً، ولا حاجة لأي إعداد يدوي).

## البنية التقنية

| الطبقة | التقنية |
|---|---|
| الواجهة | Next.js 16 (App Router) + React 19 + Tailwind CSS |
| الحساب الهندسي | JavaScript خالص، بدون أي مكتبات تصميم إنشائي جاهزة — كل معادلة مكتوبة ومُشتقة يدوياً |
| قاعدة البيانات | SQLite (عبر better-sqlite3) — قاعدة موحّدة لجميع الحاسبات |
| تصدير PDF | التقاط HTML عبر html2canvas ثم تجميعه بصفحات A4 عبر jsPDF (لضمان عرض عربي RTL سليم دون مشاكل تشكيل الحروف) |
| رمز QR | مكتبة qrcode، يُشفَّر داخله ملخص التقرير |

جرّبت كل حاسبة عبر اختبارات فعلية (يدوية وبرمجية) قبل التسليم، وتم التحقق يدوياً من تطابق
الأرقام الناتجة مع الحساب اليدوي للتأكد من عدم وجود أي قيم وهمية أو تقريبية.

## دليل الحاسبات وأساس كل حساب

### 1) القواعد المنفصلة (S-01-A)
تحديد الأبعاد من مساحة التحمل المطلوبة (P/qa الصافية)، ثم تكرار العمق الفعال حتى تحقيق
**فحصي القص الثاقب الكامل** (المعادلات الثلاث لـ ACI 318 §22.6.5.2 مع βc وαs) **والقص أحادي
الاتجاه**، ثم تصميم الانحناء بطريقة Rn-ρ عند وجه العمود.

### 2) القواعد المشتركة والشريطية (S-01-B)
تدعم عمودين أو أكثر (عمودان، ثلاثة أعمدة، أو شريطية لعدد أكبر) عبر **محرك واحد**: يُحسب طول
القاعدة بحيث يطابق مركزها محصلة الأحمال، ثم يُحل **مخطط القص والعزم فعلياً بالتكامل العددي**
(Statics) بدلاً من معادلة جاهزة — هذا يضمن دقة العزم الموجب (سفلي) والسالب (علوي فوق الأعمدة)
مهما اختلف عدد الأعمدة أو تباعدها.

### 3) القواعد المرتبطة Strap (S-01-C)
عمود حافي مقيّد بحد الملكية + عمود داخلي، مرتبطان بجسر لا يلامس التربة. تُحل اللامركزية
وقوة القص المنقولة عبر الجسر بمعادلة اتزان العزم، ثم تُصمَّم كل قاعدة بشكل منفصل وفق رد
الفعل الفعلي بعد أثر الرافعة.

### 4) اللبشة (S-02)
**الطريقة الجاسئة (Rigid/Conventional Method)**: توزيع ضغط التربة بمعادلة الإجهاد المحوري +
الانحناء ثنائي المحور (P/A ± M·c/I) عند أركان اللبشة، فحص قص ثاقب عند أثقل عمود، وتصميم
شرائح تمثيلية بمعاملات عزم الكمرات المستمرة على التباعد الفعلي المُستخرج من إحداثيات الأعمدة.

### 5) الأعمدة (S-03)
معادلة القدرة المحورية القصوى φPn = ασφ[0.85f'c(Ag−Ast)+fyAst] (ACI 318)، مع فحص نحافة
kLu/r مبسّط.

### 6) الكمرات (S-04)
الوزن الذاتي محسوب فعلياً من الأبعاد (وليس تقديراً)، معاملات عزم ACI للحالات الأربع (بسيط،
كابولي، مستمر، مستمر من طرف واحد)، تصميم Rn-ρ، تصميم كانات القص الكامل (بما فيه حد تصغير
التباعد عند القص المرتفع)، وفحص سماكة الترخيم الدنيا (ACI Table 9.3.1.1).

### 7) البلاطات (S-05)
- **أحادية الاتجاه**: نفس منهجية الكمرات لكن بعرض 1م + حديد انكماش/حرارة.
- **ثنائية الاتجاه**: توزيع الحمل بين الاتجاهين بطريقة **توافق الانفراف** (wx = w·Ly⁴/(Lx⁴+Ly⁴))
  وهي طريقة تحليلية تُشتق حسابياً من الأبعاد مباشرة (بلا جداول معاملات جاهزة عرضة للخطأ)، ثم
  تصميم كل اتجاه بمعاملات العزم المستمر.

### 8) الجدران (S-06)
تسليح أدنى وفق ACI 318 §11.6، مع خيار **جدار استنادي** يُصمَّم كعنصر كابولي رأسي تحت ضغط
تربة حقيقي بنظرية Rankine (Ka = tan²(45°−φ/2))، والعزم والقص مُشتقّان بالتكامل الرياضي للحمل
المثلثي المتزايد.

### 9) السلالم (S-07)
معادلة الراحة 2R+T=630mm لاشتقاق عدد وارتفاع القوائم من الارتفاع الكلي فعلياً، حجم القلبة
والدرجات من الهندسة الفعلية (الطول المائل، المثلثات)، تصميم انحناء كبلاطة مائلة. يدعم مستقيم
وL وU (فَرشتان + بسطة) بالإضافة إلى **دائري/حلزوني** (تصميم كابولي شعاعي من عمود مركزي، بمساحة
قطاع دائري حقيقية = 0.5(Rout²−Rin²)Δθ).

### 10) الخزانات (S-08)
**مستطيلة**: جدار كابولي تحت ضغط هيدروستاتيكي مثلثي (Mu=γwH³/6 مُشتقة بالتكامل).
**دائرية**: نظرية شد الطوق الكلاسيكية T=γw·h·R. يشمل تصميم سقف (بلاطة مستطيلة أو دائرية
بمعادلات الصفائح الدائرية الكلاسيكية)، ومساحات العزل واللياسة.

### 11) المسابح (S-09)
تصميم الجدار على **أسوأ حالتين فعلياً ويُقارن بينهما**: الامتلاء (ضغط ماء للخارج) والفراغ تحت
منسوب الأرض (ضغط تربة Rankine للداخل)، مع فحص رفع (Uplift) عند الفراغ، وحساب تدفق المضخة
المطلوب من حجم المسبح ومدة دورة التنقية.

### 12) حاسبة المواد (متكاملة في كل حاسبة + أداة مستقلة S-10)
طريقة **الحجم الجاف** (معامل 1.54) بالنسب الحجمية القابلة للتخصيص الكامل (رتبة، نسبة خلط،
نوع أسمنت، نسبة هدر، نسبة ماء/أسمنت)، وليست جدول أرقام جاهزة.

## ملاحظات منهجية بالشفافية الكاملة
- منهجية اللبشة والبلاطات ثنائية الاتجاه والخزانات هي طرق مبسّطة معتمدة هندسياً (وليست تحليل
  عناصر محددة FEM) — مناسبة لمعظم الحالات العملية، مع الإشارة صراحة داخل نتائج كل حاسبة إلى
  متى يُنصح بتحليل أدق.
- تصميم برج/أعمدة دعامة الخزان العلوي، واستقرار الجدار الاستنادي الكامل (انزلاق/انقلاب)، خارج
  نطاق هذا التسليم (يُستكملان عبر حاسبتي الأعمدة والكمرات، أو يمكن إضافتهما كوحدة مستقلة لاحقاً).
- تأثيرات الالتواء في العمود المركزي للدرج الدائري غير مُصمَّمة تفصيلياً (يُنصح بمراجعة هندسية إضافية).

# القسم الثاني — حاسبة حديد التسليح (Bar Bending Schedule)

حاسبة تفصيل حديد كاملة ومستقلة عن التصميم الإنشائي: يُدخل المهندس أبعاد العنصر وتوزيع الحديد
المُعتمد (من القسم الأول أو من مخطط تنفيذي جاهز)، فتُخرج الحاسبة **جدول تفصيل حديد كامل**
(نوع كل مجموعة أسياخ، القطر، الطول الفعلي للقطعة الواحدة شاملاً الخطافات، العدد، عدد الأسياخ
التجارية ووصلات التراكب اللازمة، الوزن، والتكلفة)، دون أي معامل تقريبي ثابت.

## المحرك الحسابي المشترك (`lib/calc/rebar/core.js`)
كل الأطوال التالية حقيقية 100%، مُشتقة من القطر ومقاومة الخرسانة وإجهاد الحديد الفعليين وفق
**ACI 318-19 §25** (وليست معاملاً جاهزاً كـ ×1.15):

- **طول التثبيت (Development Length)**: المعادلة العامة الكاملة `ld = fy·ψt·ψe·ψs·ψg / (1.1·λ·√f'c·(cb/db)) × db`
  باستخدام الغطاء/التباعد الفعليين لحساب `cb`، مع `Ktr=0` كتبسيط محافظ مسموح به صراحة في الكود.
- **طول تثبيت الخطاف (Hooked Bar)**: معادلة ACI 318-19 الجديدة `ldh = 0.24·fy·ψe·ψc·ψr/√f'c × db`.
- **طول التراكب**: شد (Class A = 1.0×ld أو Class B = 1.3×ld) وضغط (وفق §25.5.5 بمعامل تصحيح
  عند خرسانة أضعف من 21MPa).
- **هندسة الخطافات (90°/135°/180°)**: طول حقيقي = امتداد مستقيم (12db أو 4db/65مم للحديد
  الرئيسي، 6db/75مم للكانات) **+ طول قوس الانحناء الفعلي** المحسوب من قطر الانحناء القياسي
  (6db/8db/10db حسب حجم السيخ) — وليس رقماً تقريبياً.
- **تقسيم الأسياخ التجارية (12م)**: عند تجاوز الطول المطلوب الطول التجاري، تُحسب أطوال التراكب
  الفعلية وعدد القطع والوصلات اللازمة تلقائياً.
- **وزن المتر الطولي**: من الكثافة الفعلية للفولاذ (7850 kg/m³) مباشرة، وليس من جدول جاهز.

## مكتبة الكانات (`lib/calc/rebar/stirrups.js`)
مستطيلة، مربعة، دائرية، متعددة الأضلاع، ومزدوجة (بأشواط إضافية/Cross-ties) — كل شكل يُحسب على
**محور السيخ الفعلي** (لا تقريب) مع طول الخطاف المطابق للقطر.

## مكتبة الأسعار وقاعدة البيانات
جدول `steel_price_lists` مستقل يخزّن قوائم أسعار متعددة (لكل مشروع أو عامة)، يمكن اختيار أي
منها مباشرة داخل أي حاسبة، وتُطبَّق التكلفة على **الوزن شامل الهدر** (وليس الصافي) بالترتيب:
حديد ← قص ← تشكيل ← تركيب ← نقل ← خصم ← ضريبة.

## ملاحظات شفافية إضافية (القسم الثاني)
- امتداد الحديد داخل المساند (الأعمدة/البسطات) يُفحص فعلياً مقابل طول التثبيت المطلوب؛ إن لم
  يكفِ العرض المتاح، تُضيف الحاسبة خطاف 90° تلقائياً وتوضح ذلك في قسم الملاحظات الهندسية.
- عدد بلوكات الهوردي المذكور استرشادي لأغراض حصر الكميات فقط (بمقاس بلوك طولي نمطي 40 سم)،
  وليس جزءاً من التصميم الإنشائي للبلاطة (ذلك ضمن القسم الأول).
- تأثيرات العزم الالتوائي والانحناء ثنائي المحور للعمود المركزي في السلم الدائري خارج نطاق
  حاسبة تفصيل الحديد (تخص التصميم الإنشائي في القسم الأول).

# القسم الثالث — نظام حصر الكميات (Quantity Takeoff)

## الفكرة المعمارية
بدل كتابة معادلة مستقلة لكل صنف من الأصناف الثمانين تقريباً الموزّعة على 14 تخصصاً (أعمال
ترابية، خرسانة، حديد، مباني، لياسة، عزل، أرضيات، أسقف تشطيب، دهانات، نجارة، ألمنيوم وزجاج،
كهرباء، صحي، طرق)، بُني القسم على سبع دوال هندسية بدائية فقط (`lib/boq/primitives.js`: حجم
صندوقي، حجم أسطواني، حجم طبقة، مساحة ناقص فتحات، طول إجمالي، عدد إجمالي، إدخال يدوي)، وسجل
أصناف (`lib/boq/categoryRegistry.js`) يربط كل صنف بالدالة المناسبة له وحقول إدخاله. هذا يحقق
مبدأ DRY المطلوب صراحة في المواصفة، ويجعل إضافة صنف جديد (بما فيها الأصناف المخصّصة التي
يضيفها المستخدم من الواجهة) مجرد سطر تعريف جديد لا دالة حساب جديدة.

## التكامل الحقيقي مع القسمين الأول والثاني
هذه هي النقطة الأهم في هذا القسم: عناصر الخرسانة وحديد التسليح في حصر الكميات **لا تُعيد
اشتقاق الكمية بمعادلة مبسّطة خاصة بها**. بدلاً من ذلك:
- عنصر حديد تسليح في BOQ يُربط إلزامياً (`rebar_link`) بحساب محفوظ فعلياً في القسم الثاني،
  ويسحب `results.totals.totalWeightKg` منه مباشرة — أي الوزن النهائي شاملاً الوصلات
  والخطافات والكانات كما فصّلته حاسبة BBS الحقيقية، لا تقديراً تقريبياً. البديل الوحيد هو
  إدخال الوزن يدوياً (لا معامل تقريبي بديل - ممنوع صراحة في متطلبات القسم).
- عنصر خرسانة في BOQ يمكن ربطه اختيارياً بحساب محفوظ في القسم الأول ليسحب
  `results.quantities.concreteVolumeM3` الفعلي (المصمَّم وفق ACI 318، لا صندوقاً مبسّطاً)،
  ثم يُشغَّل عليه محرك حصر مواد الخرسانة نفسه من `lib/calc/materials.js` (لا نسخة موازية
  منه) لإنتاج كميات الأسمنت/الرمل/البحص. أو يُدخَل هندسياً مباشرة (طول×عرض×سماكة) للتقدير
  السريع في مراحل مبكرة لا تحتاج تصميماً إنشائياً كاملاً بعد.
- تحقّق من هذا التكامل فعلياً اختبار حيّ (وليس Mock) في `tests/`: إنشاء حساب حديد وحساب عمود
  حقيقيين عبر `/api/calculate`، حفظهما، ثم ربطهما بعنصرَي BOQ والتحقق أن الكمية المسحوبة
  تطابق نتيجة الحاسبة الأصلية تماماً.

| الصيغة | الحالة | التفاصيل |
|---|---|---|
| Excel / CSV | ✅ كامل | أعمدة قياسية (نموذج قابل للتنزيل من واجهة الاستيراد)، تحقّق ورفض لكل صف مع السبب |
| DXF | ✅ حقيقي، محدود النطاق | قراءة هندسة فعلية (إحداثيات حقيقية) لعناصر LINE/LWPOLYLINE/CIRCLE، تجميع حسب الطبقة (Layer)، طول فعلي ومساحة فعلية (صيغة Shoelace). **لا** يوجد تصنيف تلقائي لربط اسم الطبقة بصنف BOQ — المستخدم يُعيّن ذلك يدوياً لكل طبقة في واجهة المعاينة، لأن اسم الطبقة وحده لا يكفي هندسياً لتحديد نوع العنصر أو سماكته |
| IFC (BIM) | ✅ حقيقي، محدود النطاق | مُحلِّل نصي كامل لصيغة STEP/SPF (بلا مكتبة خارجية) يستخرج الكيانات الإنشائية المعروفة وأي `IfcElementQuantity` مرتبطة بها فعلياً في الملف. **لا** يوجد محرك تمثيل هندسي ثلاثي الأبعاد (B-rep) لإعادة بناء كميات من الهندسة الخام إن لم يُصدّرها برنامج BIM كمجموعة كميات جاهزة — العنصر بلا مجموعة كميات يُعاد `null` صراحة ويُطلب إدخاله يدوياً، لا تخميناً |
| DWG | ❌ غير مدعوم | صيغة ثنائية مملوكة تتطلب مكتبة تحويل تجارية (لا تتوفر مجاناً)؛ الحل: تصدير DXF من برنامج الرسم (Save As) ثم استيراده |
| PDF | ❌ غير مُفعَّل في هذا الإصدار | استخراج جداول من تخطيطات PDF المتفاوتة غير موثوق بما يكفي لإدراجه دون مراجعة يدوية شبه كاملة لكل حالة؛ استخدم Excel/CSV/DXF/IFC بدلاً منه |

كل مسارات الاستيراد (بما فيها DXF/IFC بعد تعيين الأصناف) تمر بخطوة معاينة `{valid, rejected}`
قبل أي كتابة في قاعدة البيانات، ثم إدراج جماعي داخل معاملة واحدة (`bulkInsertBoqElements`)
يتحقق من التكرار لكل صف، ويُنتج سجل استيراد (`boq_imports`) يوثّق عدد المستورد والمرفوض وسببه.

## الذكاء الاصطناعي (`lib/boq/ai.js`)
مساعد اختياري (يتطلب `ANTHROPIC_API_KEY` في بيئة الخادم — بدونه يُعيد خطأ واضح لا فشلاً صامتاً
ولا نتيجة ملفّقة) يحلّل صورة مخطط عبر Claude Vision. يلتزم حرفياً بقواعد القسم الخامس
الإلزامية: لا يخترع بعداً غير مكتوب على المخطط، يُرفق كل اقتراح بمستوى ثقة (0–1) ومبرر نصي،
ولا يكتب أي شيء في قاعدة البيانات بنفسه — كل اقتراح يمر عبر نفس مسار "إضافة عنصر" اليدوي
العادي بعد مراجعة المستخدم واعتماده صراحةً لكل عنصر على حدة (زر "اعتماد وإضافة" في `/dashboard/boq/ai`).

## الأمان — ما هو حقيقي وما هو خارج نطاق هذا التسليم
- **حماية SQL Injection**: حقيقية وكاملة — كل استعلام في `lib/db.js` عبارة عن Prepared
  Statement بمعاملات مُسمّاة عبر `better-sqlite3`؛ لا يوجد تجميع نصوص SQL يدوي في أي مسار.
- **حماية XSS**: تلقائية من React (لا يوجد `dangerouslySetInnerHTML` في أي مكوّن من مكوّنات
  هذا القسم).
- **المعاملات (Transactions)**: حقيقية — كل عملية إنشاء/تعديل/حذف/استيراد جماعي مُغلَّفة في
  `db.transaction()`، بما يضمن تراجعاً كاملاً عند أي فشل جزئي.
- **سجل التدقيق (Audit Log)**: حقيقي وكامل — كل تعديل يُسجَّل بحالته قبل وبعد في
  `boq_audit_log`، ويُحتفَظ بالسجل حتى بعد حذف العنصر نفسه.
- **الترقيم الصفحي والفهرسة**: حقيقية — فهارس فعلية على `project_id`/`category_key` في
  SQLite، واختبار أداء (وليس مجرد ادّعاء) يُدرج 3000 عنصر ويقيس زمن استعلام صفحة واحدة منها.
- **RBAC (صلاحيات متعددة المستويات) والتشفير**: **غير مُنفَّذين في هذا التسليم** — التطبيق
  الأساسي بأكمله (الأقسام 1 و2 أيضاً) لا يحتوي أي نظام مصادقة (تسجيل دخول) من الأصل، وإضافة
  صلاحيات حقيقية بلا نظام مصادقة يسبقها غير ذي معنى. حقل `actor` النصي الاختياري موجود في
  `boq_audit_log` جاهزاً للربط بنظام مصادقة إن أُضيف لاحقاً، دون الحاجة لإعادة هيكلة.
- لم يخضع أي مما سبق لاختبار اختراق فعلي (Penetration Testing) — "حماية حقيقية من حيث
  البنية" لا تعني "مُدقَّقة أمنياً من طرف مستقل"، والفرق بينهما مهم قبل أي استخدام إنتاجي حسّاس.

## الاختبارات
`tests/boq/` — 139 اختبار حقيقي (لا Mock إلا حيث ذُكر صراحة) عبر `node --test`:
- `calc-engine.test.js`: كل دالة بدائية + **كل الأصناف الثمانين في السجل تُختبر فعلياً عبر
  المحرك الكامل** (وليس عيّنة يدوية) — هذا بالضبط ما اكتشف واختبار انحداره أثناء البناء عدم
  تطابق سابق بين اسم حقل في السجل ومعامل الدالة المقابلة له.
- `db.test.js`: قاعدة بيانات SQLite فعلية (لا محاكاة) — دورة حياة عنصر كاملة، اكتشاف تكرار،
  سجل تدقيق، استيراد جماعي، لوحة تحكم، ترقيم صفحي، وفحص أداء بـ3000 سجل.
- `importers.test.js`: عيّنات CSV/Excel/DXF/IFC حقيقية مصنوعة يدوياً (لا بيانات وهمية).
تشغيل: `node --test tests/boq/*.test.js`. إضافة لذلك، رُكِّض تطبيق فعلي (`next dev`) واختُبرت
كل نقاط API ال15 وكل صفحات الواجهة الست عبر HTTP حقيقي (وليس فقط اختبارات وحدة) قبل التسليم،
بما في ذلك سيناريو الربط الكامل بين الأقسام الثلاثة بأرقام حقيقية من طرف لطرف.

# القسم الرابع — نظام إدارة المشاريع (Project Management System)

## الفكرة المعمارية
هذا القسم هو "القلب الرئيسي للنظام" كما وصفته المواصفة، فبُني ليكون الطبقة التي تُظلّل بقية
الأقسام لا طبقة موازية لها:
- **لا جدول `pm_projects` منفصل.** جدول `projects` الموجود أصلاً (والذي تعتمد عليه حاسبات
  القسم الأول وحديد القسم الثاني وعناصر BOQ في القسم الثالث عبر `project_id`) وُسِّع بأعمدة
  جديدة فقط (`ALTER TABLE ADD COLUMN` بفحص `PRAGMA table_info` أولاً، فعّالة التكرار/Idempotent)
  ليحمل كل الحقول الغنية (المالك، المقاول، الاستشاري، مدير المشروع، الإحداثيات، الميزانية،
  الحالة...). هذا يحقق حرفياً ما وثّقه README القسم الثالث سابقاً: "قاعدة البيانات مصمَّمة
  لتكون نواة موحّدة يمكن أن تُبنى عليها إدارة المشاريع الكاملة دون الحاجة لإعادة هيكلة".
- كل الجداول الجديدة (20 جدولاً) ببادئة `pm_` (نفس نمط `boq_*`)، مُعرَّفة ومُهيَّأة بالكامل في
  `lib/pm/schema.js` وحده — **لم يُعدَّل `lib/db.js` بحرف واحد**، صفر تأثير على الأقسام 1-3.
- طبقة الوصول لقاعدة البيانات مقسَّمة إلى 16 وحدة مستقلة تحت `lib/pm/db/` (مشاريع، مراحل،
  مهام، فريق، ميزانية، موارد، مخاطر، جودة، سلامة، مستندات، اجتماعات، تنبيهات، تدقيق، تقارير،
  إحصاءات) بدل ملف واحد ضخم — تطبيق حرفي لقاعدة "Modular Architecture" الإلزامية.

## محرك المسار الحرج (Critical Path Method) — `lib/pm/criticalPath.js`
أهم قطعة منطق حقيقية في هذا القسم: تمريرتان فعليتان (أمامية لحساب ES/EF، خلفية لحساب LS/LF)
تدعمان أنواع التبعية الأربعة القياسية (FS/SS/FF/SF) مع فترات تأخر/تقديم بالأيام، وترتيباً
طوبولوجياً حقيقياً بخوارزمية Kahn يكتشف أي دورة تبعيات (Circular Dependency) ويرفضها بخطأ
واضح بدل نتيجة غير معرَّفة. الطفو الحر (Float) والمسار الحرج يُشتقّان حسابياً من الفرق بين
LS وES لكل مهمة، لا يُقدَّران. مُختبَر بـ10 اختبارات وحدة حقيقية تغطي: سلسلة خطية، مسارات
متوازية بطفو، الأنواع الأربعة، وكشف الدورات (`tests/pm/criticalPath.test.js`).

## التكامل الحقيقي مع الأقسام الثلاثة الأولى
تبويب "نظرة عامة" في كل مشروع يعرض فعلياً (استعلام SQL حي، لا رقماً ثابتاً): عدد الحسابات
الهندسية (`calculations`) المرتبطة بنفس `project_id`، وعدد عناصر حصر الكميات وتكلفتها
الإجمالية من `boq_elements` لنفس المشروع (`lib/pm/db/projectStats.js`). أي حساب خرسانة أو
حديد أو عنصر BOQ يُنشأ لمشروع من هذه الواجهات الثلاث يظهر فوراً هنا، لأنها الجدول نفسه لا نسخة منه.

## الذكاء الاصطناعي (`lib/pm/ai.js`)
نفس نمط `lib/boq/ai.js` تماماً — يتطلب `ANTHROPIC_API_KEY` (خطأ واضح بدونه)، ولا يكتب أي شيء
في قاعدة البيانات بنفسه. أربع قدرات تطبّق البند الثالث عشر الإلزامي حرفياً ("لا يعتمد أي قرار
نهائي بدون موافقة المستخدم"، "يجب توضيح سبب كل توصية"، "استخدام البيانات الفعلية فقط"): تحليل
صحة المشروع (تقدم/تأخير/أسباب/حلول مقترحة) من بيانات المشروع الحقيقية، تلخيص محاضر الاجتماعات،
الإجابة عن استفسارات حرة بالاعتماد حصراً على البيانات المُرسَلة، وفقرة سردية تفسّر أرقام تقرير
محسوب فعلياً دون اختراع أرقام جديدة. كل استجابة JSON منظّمة تحمل حقل `reasoning` يوضح الأساس.

## الصلاحيات (`lib/pm/roles.js`) — ما هو حقيقي بالضبط
مصفوفة صلاحيات كاملة لـ14 دوراً × 12 وحدة × 4 إجراءات (عرض/تعديل/حذف/اعتماد)، **مُنفَّذة
ومُفعَّلة فعلياً**: كل مسار API في `/api/pm/*` يستقبل `actor_role` صراحةً ويرفض الطلب (403
حقيقي) إن لم يملك الدور صلاحية الإجراء — وليست مجرد واجهة تعرض/تخفي أزراراً شكلياً. الفجوة
الوحيدة، بشفافية كاملة: التطبيق بأكمله (الأقسام 1-3 أيضاً) **لا يحتوي نظام مصادقة/تسجيل دخول
من الأصل**، فـ"الدور الحالي" في الواجهة (`ActorBar`) اختيار من المتصفح محفوظ محلياً، وليس
هوية مُتحقَّق منها بجلسة آمنة. حقلا `actor`/`actor_role` جاهزان تماماً للربط بنظام مصادقة
حقيقي لاحقاً دون أي تغيير في منطق المصفوفة نفسه.

## الأمان — ما هو حقيقي وما هو خارج نطاق هذا التسليم
- **SQL Injection / XSS / المعاملات / سجل التدقيق / الترقيم الصفحي والفهرسة**: حقيقية وكاملة،
  بنفس الأساس الذي وثّقه القسم الثالث أعلاه حرفياً — Prepared Statements في كل استعلام،
  React بلا `dangerouslySetInnerHTML`، `db.transaction()` لكل عملية مركّبة، فهارس فعلية على
  كل عمود `project_id` ومعظم أعمدة التاريخ/الحالة.
- **الصلاحيات (RBAC)**: حقيقية وفعّالة كما فُصِّل أعلاه، بفجوة واحدة موثّقة (لا مصادقة).
- **CSRF**: غير مُعالَج بتوكن مخصّص في هذا التسليم — نفس وضع الأقسام 1-3 سابقاً.
- **المصادقة الثنائية (2FA) والتشفير عند الراحة (Encryption at Rest)**: **غير منفَّذين** —
  يتطلبان نظام مستخدمين/جلسات حقيقياً كأساس أول، وهو غير موجود بعد في التطبيق كما وثّقنا.
- **تخزين المستندات**: حقيقي على قرص الخادم المحلي (`data/pm-uploads/`) لا تخزيناً سحابياً/CDN؛
  يحتاج نسخاً احتياطياً لهذا المجلد ولملف SQLite معاً في أي بيئة إنتاج فعلية.
- **الإشعارات (بريد/SMS)**: التنبيهات مُخزَّنة وحقيقية داخل التطبيق، لكن لا يوجد إرسال فعلي
  خارج التطبيق (يتطلب مزوّد بريد/SMS وعامل خلفي دائم غير متوفرين في هذا الـ stack).
- لم يخضع أي مما سبق لاختبار اختراق فعلي، تماماً كتنويه القسم الثالث.

# القسم السادس — نظام إدارة الأعمال (Business Management System)

نظام إدارة أعمال هندسية متكامل لشركات المقاولات والمكاتب الاستشارية، يربط الجانب التجاري
(عملاء، فرص، عروض أسعار) بالعقود والتنفيذ (أوامر تغيير، مستخلصات، أوامر عمل) وبقاعدة البيانات
المركزية نفسها التي تستخدمها الأقسام 1-5. **ليس صفحة CRM بسيطة** - كل عملية تعمل فعلياً من
البداية للنهاية وتُخزَّن في SQLite حقيقية، بلا بيانات وهمية ولا أزرار شكلية.

## الفكرة المعمارية

نفس نمط `lib/pm/` و`lib/schedule/` حرفياً: `lib/business/schema.js` يعيد استخدام اتصال SQLite
الموحّد من `lib/db.js` (لم يُعدَّل إطلاقاً) ويضيف 21 جدولاً ببادئة `biz_`، بالإضافة إلى عمود واحد
جديد (`client_id`) على جدول `projects` نفسه لربط كل مشروع تنفيذي بعميل CRM حقيقي بدل حقل
`client_name` النصي الحر القديم (الذي يبقى للتوافق مع المشاريع غير المربوطة بعد).

**الصلاحيات (RBAC) لم تُستنسخ في ملف منفصل** - بل امتدّ `lib/pm/roles.js` نفسه (تماماً كما فعل
القسم الخامس) بـ10 وحدات صلاحية جديدة (`biz_client`, `biz_opportunity`, `biz_quote`,
`biz_contract`, `biz_partner`, `biz_work_order`, `biz_payment`, `biz_correspondence`,
`biz_meeting`, `biz_commitment`) و3 أدوار جديدة (مدير الأعمال، مسؤول العقود، مسؤول المشتريات)،
فأصبحت المصفوفة الآن 18 دوراً × 23 وحدة. هوية الفاعل (actor/actor_role) في الواجهة هي **نفسها**
المخزَّنة في `localStorage('pm_actor')` التي تستخدمها الأقسام 4 و5 - شخص واحد بدور واحد عبر كل
التطبيق، لا اختيار دور منفصل لكل قسم.

المقاولون والموردون (البندان 6 و7) موحَّدان في جدول واحد `biz_partners` (بعمود `partner_type`
مميِّز) بدل جدولين متطابقَي البنية تقريباً - نفس فلسفة `biz_payment` التي تخدم معاً المستخلصات
(البند 9) وأوامر التغيير التجارية (البند 10) لأن كلتيهما عملية مالية على نفس العقد بنفس دورة
اعتماد. هذا تقليل حقيقي للتكرار (البند 24) وليس نقصاً في التغطية - كل حقل مطلوب في كل بند من
القواعد الإلزامية موجود فعلياً.

## التكامل الحقيقي (وليس مجرد نية)

- **عرض السعر ← حصر الكميات**: كل بند عرض سعر يمكن ربطه بـ`boq_element_id` حقيقي من جدول
  `boq_elements` الفعلي للقسم الثالث (البند 4: "ربط عرض السعر مباشرة مع حصر الكميات").
- **عرض السعر ← عقد**: تحويل عرض سعر "فائز" إلى عقد (`convertQuoteToContract`) ينسخ القيمة
  والعميل والشروط فعلياً، ويمنع تكرار التحويل لنفس العرض.
- **أمر التغيير ← ميزانية المشروع**: اعتماد أمر تغيير (وليس مجرد إنشاؤه) هو اللحظة الوحيدة التي
  تُحدَّث فيها `current_value` للعقد (البند 10 حرفياً)، وإن كان العقد مرتبطاً بمشروع تنفيذي حقيقي
  فإن الاعتماد يستدعي `createBudgetItem` من `lib/pm/db/budget.js` مباشرة (استيراد فعلي بين
  القسمين) فيُسجَّل بند `change_order` حقيقي في ميزانية القسم الرابع - لا نسخة موازية من الرقم.
- **صرف مستخلص ← إيراد فعلي في الميزانية**: بنفس المنطق، تسجيل صرف مستخلص (`markProgressPaymentPaid`)
  يسجّل بند `revenue` حقيقياً في `pm_budget_items` للمشروع المرتبط.
- **قرار اجتماع ← مهمة فعلية في الجدول الزمني**: إضافة قرار من اجتماع أعمال مرتبط بمشروع، مع
  تفعيل خيار "إنشاء مهمة"، يستدعي `createTask` من `lib/pm/db/tasks.js` فعلياً (البند 12: "ربط
  المهام الناتجة مباشرة بقسم إدارة المشاريع والجدول الزمني") - وليس نصاً منفصلاً غير متصل بشيء.
- **Workflow اعتماد عام**: جدول `biz_approvals` يسجّل لكل قرار حساس (اعتماد عرض سعر/عقد/أمر
  تغيير/مستخلص) من وافق، متى، القرار، والملاحظات - تماماً كما يطلب البند 18.

## النطاق الحقيقي لكل وحدة (بصراحة تامة، بلا مبالغة)

- **التصدير**: Excel وCSV حقيقيان (نفس مولّدات `lib/pm/exporters/*` بالضبط، مُعاد استخدامها لا
  تكرارها) لكل تقارير القسم الـ11. تصدير PDF حقيقي أيضاً لكنه من جهة العميل (متصفح، عبر
  `exportNodeToPdf` الموجودة أصلاً في `lib/pdfExport.js` لنفس سبب استخدامها في التقارير الهندسية:
  تفادي مشاكل تشكيل الحروف العربية في مكتبات PDF الخادمية). لا يوجد مولّد Word (.docx) في هذا
  التسليم - قرار نطاق واعٍ وليس إغفالاً، لعدم وجود أي بنية تحتية له في المشروع أصلاً.
- **المصادقة الثنائية (2FA) والتشفير الكامل لكل حقل حساس**: خارج نطاق هذا التسليم - النظام كله
  (بما فيه الأقسام 1-5) لا يملك طبقة مصادقة حقيقية أصلاً (لا جلسات، لا كلمات مرور)؛ الفاعل يُمرَّر
  صراحة كما هو موثَّق بدقة في `lib/pm/roles.js` نفسه. إضافة تشفير/2FA حقيقيين تتطلب طبقة مصادقة
  كاملة للتطبيق بأسره، وهذا تغيير معماري أكبر من نطاق قسم واحد.
- **الإشعارات**: حقيقية ومُخزَّنة (`biz_notifications`) ومُشتقة من بيانات حية (عقد يقترب من
  الانتهاء، عرض سعر منتهي الصلاحية، مستخلص متأخر، التزام متأخر، أمر تغيير/مستخلص بانتظار اعتماد)
  - بلا آلية دفع فعلية (بريد/SMS)، بنفس صراحة توثيق القسم الرابع لنفس القيد بالضبط.
- **الأداء**: Pagination حقيقي على كل القوائم (`page`/`pageSize`)، وفهارس SQLite على كل عمود
  بحث/تصفية متكرر. لا Caching ولا Background Jobs في هذا التسليم (SQLite محلية لا تحتاجها بنفس
  إلحاح قاعدة بيانات مركزية بعيدة؛ يبقى قابلاً للإضافة لاحقاً دون تغيير الواجهات).

`lib/business/ai.js` يستدعي Claude Sonnet 5 فعلياً (نفس نمط `lib/pm/ai.js` بالضبط: JSON صِرف،

موردين، تحليل أداء شريك، اكتشاف مصروفات/أسعار غير معتادة، تحليل عقد، تلخيص مراسلات، استخراج
التزامات من نص مستند، ملخص تنفيذي من المؤشرات الحية، وسؤال حر. **كل مخرجاته اقتراحات للمراجعة
البشرية فقط** (البند 20 حرفياً) - لا يكتب أي دالة ذكاء اصطناعي أي شيء في قاعدة البيانات مباشرة؛
أي إجراء فعلي (اعتماد، رفض، إنشاء) يمر حصراً عبر مسارات `db/*` والتحقق من الصلاحيات العادي.

## الصلاحيات (تفصيل إضافي)

أمثلة فعلية من المصفوفة (وليست افتراضات نظرية) — تحقّقنا منها جميعاً باختبارات حقيقية:
مدير الأعمال يملك صلاحية كاملة + اعتماد على كل الوحدات التجارية؛ مسؤول العقود يعتمد العقود

الفرص الداخلية؛ المحاسب يعتمد الدفعات مالياً لكن لا يعدّل الفرص التجارية؛ العميل يرى عقده وعروض
أسعاره ومستخلصاته فقط دون رؤية خط أنابيب الفرص الداخلي أو بيانات الشركاء؛ العامل والفني بلا أي
صلاحية على أي وحدة تجارية.

# القسم السابع — نظام إدارة المعدات (Equipment & Assets Management System)

نظام إدارة معدات وآليات إنشائية متكامل يغطي دورة حياة المعدة كاملة: شراء/استئجار → تسجيل →
تخصيص لمشروع → حجز → تشغيل → وقود → صيانة وقائية/تصحيحية → أعطال → قطع غيار → نقل → تكلفة →
تقارير → أرشفة. **ليس صفحة CRUD لإضافة معدات فقط** - كل عملية تعمل فعلياً من البداية للنهاية
وتُخزَّن في نفس قاعدة SQLite المركزية التي تستخدمها الأقسام 1-6، بلا بيانات وهمية ولا أزرار شكلية.

## الفكرة المعمارية

نفس نمط `lib/pm/` و`lib/schedule/` و`lib/business/` حرفياً: `lib/equipment/schema.js` يعيد استخدام
اتصال SQLite الموحّد من `lib/db.js` (**لم يُعدَّل إطلاقاً**، صفر أثر على الأقسام 1-6 العاملة فعلياً)
ويضيف 22 جدولاً ببادئة `equipment_`، منها: `equipment_assets` (السجل الرئيسي)، `equipment_categories`
(مزروعة تلقائياً بـ31 نوع معدة موزّعة على 8 مجموعات حسب البند 3، قابلة للتوسعة من لوحة التحكم)،
`equipment_assignments`/`equipment_reservations` (تخصيص/حجز مع منع تعارض حقيقي)، `equipment_operation_logs`
+ `equipment_hour_meter_readings` (سجل تشغيل وعداد ساعات)، `equipment_fuel_logs`،
`equipment_maintenance_schedules` + `equipment_maintenance_records`، `equipment_breakdowns`،
`equipment_spare_parts` + `equipment_spare_part_usage`، `equipment_operators` +
`equipment_operator_authorizations`، `equipment_transfers`، `equipment_rentals`، `equipment_inspections`،
`equipment_notifications`، `equipment_audit_log`، `equipment_documents`، `equipment_report_log`،
و`equipment_status_log` (سجل تاريخي كامل لكل تغيير حالة/موقع/مشروع).

**الصلاحيات (RBAC) لم تُستنسخ في ملف منفصل** - بل امتدّ `lib/pm/roles.js` نفسه (تماماً كما فعل
القسمان الخامس والسادس) بست وحدات صلاحية جديدة (`equipment`, `equipment_operation`,
`equipment_maintenance`, `equipment_spare_part`, `equipment_operator`, `equipment_rental`) وأربعة
أدوار جديدة (مدير المعدات، مسؤول الصيانة، أمين المخزن، المشغل)، فأصبحت المصفوفة الآن **22 دوراً ×
29 وحدة**. فحوصات السلامة (`equipment_inspections`) لا تملك وحدة صلاحية خاصة بها عمداً - تُدار عبر
وحدة `safety` **الموجودة أصلاً**، فربط "المعدات بقسم السلامة المهنية مباشرة" (البند 15) تكامل صلاحيات
حقيقي لا تكرار. هوية الفاعل (actor/actor_role) هي **نفسها** المخزَّنة في `localStorage('pm_actor')`
التي تستخدمها الأقسام 4-6 - شخص واحد بدور واحد عبر كل التطبيق.

"مهندس الموقع" المذكور في مواصفة القسم يُطابق الدور العام الموجود أصلاً `engineer` بدل استحداث دور
مطابق وظيفياً - نفس منطق تقليل التكرار (البند 24 في القواعد الإلزامية) المتَّبع في القسم السادس.

## التكامل الحقيقي (وليس مجرد نية)

- **تشغيل معدة ← تكلفة ← ميزانية المشروع**: تسجيل وقود، صيانة، أو إصلاح عطل لمعدة مرتبطة بمشروع
  حقيقي يستدعي `createBudgetItem` من `lib/pm/db/budget.js` **مباشرة** (استيراد فعلي بين القسمين) -
  فيظهر بند `expense` حقيقي (فئة `equipment_fuel`/`equipment_maintenance`/`equipment_breakdown`/
  `equipment_rental`) في ميزانية القسم الرابع فوراً، لا نسخة موازية من الرقم (البند 22 حرفياً:
  "تشغيل معدة → تسجيل ساعات → تحديث تكلفة → تظهر في ميزانية المشروع → تظهر في التقارير").
- **الحجز/التخصيص ← جدول المشروع**: كل تخصيص وحجز يُربط بـ`project_id` حقيقي من جدول `projects`
  نفسه (نفس أسلوب `pm_resource_assignments`)، دون المساس بمنطق حجز الموارد العام الخفيف الموجود
  أصلاً في `pm_resources` (نوع المورد `equipment` هناك يبقى كما هو لجدولة Gantt الأساسية؛ هذا
  القسم هو السجل التفصيلي الكامل لدورة حياة كل معدة على حدة).
- **تخصيص/تشغيل ← حالة المعدة تلقائياً**: تخصيص معدة نشط يحوّل حالتها إلى "قيد التشغيل" تلقائياً؛
  عطل جديد أو بدء صيانة يحوّلها إلى "في الصيانة"؛ إغلاق آخر مشكلة صيانة/عطل مفتوحة يعيدها لـ"متاحة"
  تلقائياً (`restoreStatusIfIdle` مشتركة بين `maintenance.js` و`breakdowns.js`) - لا تدخّل يدوي مطلوب.
- **فشل فحص سلامة ← إخراج فعلي من الخدمة**: نتيجة فحص "راسب" تستدعي `changeEquipmentStatus` فعلياً
  فتنقل المعدة لحالة "خارج الخدمة"، فيُرفض أي سجل تشغيل جديد عليها تلقائياً حتى اعتماد صريح لإعادة
  التشغيل عبر صلاحية `approve` على وحدة `safety` (البند 15 حرفياً).
- **مشغل غير مؤهل ← رفض صريح**: تسجيل تشغيل أو تخصيص بمشغل ليس له تفويض صريح على المعدة، ولا
  تصنيفها ضمن `allowed_categories` الخاصة به، أو برخصة منتهية، يُرفض بخطأ واضح يذكر السبب (البند 14).

## النطاق الحقيقي لهذا القسم (بصراحة تامة، بلا مبالغة)

- **GPS/تتبع لحظي فعلي**: خارج نطاق هذا التسليم - لا يوجد جهاز استشعار أو مزوّد خدمة حقيقي متاح
  للربط به. البنية جاهزة تماماً للتكامل لاحقاً (`current_location` نص حر يُحدَّث الآن يدوياً/عبر
  التخصيص والنقل؛ يمكن ربطه بمصدر GPS حقيقي لاحقاً بإضافة مسار Webhook دون أي تغيير في المخطط).
- **تنبيه "انخفاض الوقود" اللحظي**: غير مُنفَّذ حرفياً (لا مقياس مستوى خزان حي) - المُنفَّذ فعلاً
  والمبني على بيانات حقيقية هو اكتشاف **ارتفاع الاستهلاك غير الطبيعي** (مقارنة استهلاك آخر 30 يوماً
  بالمعدل المرجعي `rated_consumption_l_per_hour`)، وهو ما نصّت عليه البنود 9 و23 فعلياً وبدقة أكبر.
- **المصادقة الثنائية (2FA) والتشفير الكامل**: خارج النطاق لنفس السبب الموثَّق بدقة في كل قسم سابق -
  لا طبقة مصادقة حقيقية في المشروع بأسره بعد؛ `actor`/`actor_role` جاهزان تماماً للربط بنظام دخول
  حقيقي لاحقاً دون تغيير منطق الصلاحيات نفسه.
- **التنبيهات**: حقيقية ومُخزَّنة (`equipment_notifications`) ومُشتقة من بيانات حية (صيانة مستحقة،
  تجاوز ساعات، عطل جديد، إصلاح متأخر، انخفاض مخزون، انتهاء رخصة/ضمان/تأمين/عقد إيجار قريباً، توقف
  طويل) عبر مسح عند كل طلب (`runEquipmentNotificationScan`، نفس أسلوب القسم السادس) - بلا آلية دفع
  فعلية (بريد/SMS) ولا Background Job حقيقي، بنفس صراحة توثيق الأقسام السابقة لنفس القيد بالضبط.
- **الأداء**: Pagination حقيقي على كل القوائم، وفهارس SQLite على كل عمود بحث/تصفية/ربط متكرر (id
  المعدة، الحالة، التاريخ، التصنيف...). لا Caching ولا Background Jobs حقيقية بعد لنفس سبب الأقسام
  السابقة (SQLite محلية)؛ قابل للإضافة لاحقاً دون تغيير الواجهات.
- **تصدير PDF**: من جهة العميل (متصفح) عبر `lib/pdfExport.js` الموجود أصلاً، لتفادي مشاكل تشكيل
  الحروف العربية في مكتبات PDF الخادمية - نفس القرار المُتَّخذ في كل الأقسام السابقة. Excel وCSV
  حقيقيان خادمياً، بإعادة استخدام مباشرة لمولّدات `lib/pm/exporters/*` (لا تكرار لمنطق التصدير).

### التكامل الحقيقي (وليس نية معلنة فقط)
- **مع قسم المعدات (equipment_assets/equipment_inspections)**: اعتماد أي تصريح عمل مرتبط بمعدة
  `out_of_service` أو فشلت في آخر فحص سلامة **يُرفض فعلياً** (400 حقيقي، ليس تحذيراً شكلياً) -
  `assertEquipmentFitForPermit()` في `lib/hse/db/permits.js`. تسجيل حادث يمكن أن يستدعي
  `changeEquipmentStatus()` الحقيقية من القسم السابع فعلياً (بعلم صريح `mark_equipment_damaged`،
  وليس تحليل نص حر). equipment_id بلا قيد FK خام عمداً (تفادي ترابط ترتيب إنشاء المخططات بين
  الأقسام مع `PRAGMA foreign_keys=ON` المفعَّل في `lib/db.js`).
- **مع قسم الأعمال (biz_approvals)**: اعتماد/رفض التصاريح يُسجَّل عبر `recordApproval()` الحقيقية
  من `lib/business/db/approvals.js` المُعاد استخدامها حرفياً - بدل تكرار نفس أعمدة "من وافق/متى".
- **مع نظام المستندات (pm_documents)**: خطط السلامة/السياسات/الإجراءات/خطط الإخلاء (البند 1) تُدار
  بالكامل عبر `lib/pm/db/documents.js` الموجود فعلاً (رفع حقيقي على القرص، إصدارات، اعتماد) -
  `lib/hse/db/safetyPlans.js` طبقة رقيقة فقط تُقيِّد `category` على قيم `hse_*`. **لا جدول HSE
  منفصل لهذا الغرض** - قرار تصميم مقصود لتفادي تكرار منطق موجود فعلاً.
- **مع قسم الجودة (pm_quality_records)**: أي حادث يمكن ربطه بسجل جودة/NCR حقيقي عبر
  `linkIncidentToQualityRecord()` التي تستدعي `createQualityRecord()` الحقيقية من القسم الرابع.
- **مع الحضور (pm_attendance)**: معدلا تكرار وشدة الحوادث (البند 16) يُحسبان من
  `SUM(pm_attendance.hours)` الحقيقي لمشروع/فترة - وليسا تقديراً ثابتاً. إن كانت الساعات صفراً
  (لا حضور مسجَّل بعد) يُعاد `null` صراحة بدل رقم مضلِّل.
- **مع مواقع العمل**: عدد العاملين/المعدات/آخر تفتيش/مستوى الخطورة في `hse_sites` كلها قيم محسوبة
  حيّة (JOIN وقت الطلب) وليست أعمدة مخزَّنة قد تصبح قديمة.

### النطاق الحقيقي لكل وحدة (بصراحة تامة، بلا مبالغة)
- **سجل المخاطر + المصفوفة**: حقيقي بالكامل. الحساب فعلي (`likelihood × severity`)، النطاقات
  الأربعة ثابتة ومُختبرة (22 اختباراً حقيقياً ناجحاً)، إعادة التقييم تُخزَّن كتاريخ كامل.
- **تصاريح العمل**: دورة حياة كاملة حقيقية (مسودة→إرسال→اعتماد/رفض→تفعيل→إغلاق)، مع بوابة سلامة
  حقيقية للمعدات كما ذُكر أعلاه. **الحد الحقيقي**: التحقق من تعارض حجز نفس الفريق/المعدة بين
  تصريحين متزامنين غير مُنفَّذ - يحتاج جدولاً زمنياً حقيقياً للقوى العاملة غير موجود في المنصة بعد.
- **التفتيشات**: قوائم تحقق قابلة للتخصيص حقيقية، تسجيل بنود حي، توليد إجراء تصحيحي تلقائي حقيقي
  عند عدم المطابقة، اعتماد/إغلاق/إعادة تفتيش حقيقية. **الحد الحقيقي**: لا التقاط صور مباشر من
  الكاميرا داخل شاشة التفتيش نفسها - الرفع يتم عبر مسار مرفقات عام منفصل (`/api/hse/attachments`)
  بعد الحفظ، وليس مدمجاً inline في كل بند كما قد يوحي "التقاط الصور" حرفياً في الوثيقة الأولى.
- **الحوادث**: تسجيل كامل بكل الحقول المطلوبة (أطراف متأثرة JSON، أسباب مباشرة/جذرية، شهود...)،
  تحقيق حقيقي بحالة متدرجة، إغلاق مشروط فعلياً باكتمال التحقيق (وليس زر إغلاق حر). **الحد
  الحقيقي**: لا حساب تلقائي لـ"أيام العمل المفقودة" من نوع الإصابة - حقل `lost_days` يُدخله
  المستخدم يدوياً ضمن بيانات كل شخص متأثر (JSON)، وليس مُشتقاً من جدول تصنيف إصابات طبي معياري.
- **الإجراءات التصحيحية**: الإغلاق **لا يحدث فعلياً** بدون `approved_by` صريح - مُختبر ومُطبَّق
  حرفياً حسب البند 12، وليس مجرد حقل شكلي في النموذج.
- **PPE**: خصم/إعادة مخزون حقيقيان ضمن نفس المعاملة، تنبيه انخفاض مخزون حقيقي، حساب تاريخ انتهاء
  تلقائي من العمر الافتراضي عند عدم تحديده. **الحد الحقيقي**: لا ربط بـ RFID/باركود فعلي للتتبع
  الفردي لكل قطعة - الكمية رقمية إجمالية فقط.
- **التدريب**: حالة الشهادة (سارية/منتهية) تُحسب حياً من التاريخ الحالي عند كل قراءة - وليست علماً
  ثابتاً قد يصبح قديماً. **الحد الحقيقي**: لا تكامل مع منصة اختبارات إلكترونية خارجية - درجة
  التقييم رقم يُدخله المستخدم يدوياً.
- **المواد الخطرة ومعدات الإطفاء**: سجلات وفحوصات دورية حقيقية بتواريخ استحقاق فعلية. **الحد
  الحقيقي**: بطاقة SDS تُرفَع كملف عبر مسار المرفقات العام (`sds_attachment_id`) - لا قاعدة بيانات
  GHS/كيميائية مدمجة تتحقق تلقائياً من تصنيف المادة أو تقترح معدات الوقاية المطلوبة تلقائياً؛
  المستخدم يُدخل هذه الحقول نصياً بناءً على بطاقة SDS الفعلية للمادة.
- **الطوارئ**: خطط/فرق/تدريبات إخلاء حقيقية بحقول مهيكلة قابلة للاستعلام (وليست نصاً حراً داخل
  ملف PDF فقط). **الحد الحقيقي**: لا محاكاة تفاعلية لسيناريو الإخلاء - تسجيل تدريب فعلي بعد وقوعه.
- **الذكاء الاصطناعي**: انظر القسم المخصص أدناه.
- **التنبيهات**: تسعة محفزات حقيقية (البند 18 السبعة + اثنان إضافيان من الوثيقة الأولى) تُفحص من
  بيانات حقيقية عند كل طلب - **بلا Cron/Background Job منفصل**، لنفس السبب الذي وثّقه القسم
  السابع عن نفسه بالضبط: بيئة Next.js API routes الخالصة هذه بلا مُجدوِل مستقل. لا إرسال بريد/SMS
  فعلي - التنبيهات داخل التطبيق فقط (in-app)، مخزَّنة وقابلة للقراءة/التعليم كمقروءة فعلياً.
- **التقارير**: عشرة أنواع تقارير حقيقية، بأربع صيغ تصدير **حقيقية وليست وهمية**: Excel وCSV
  (عبر مُصدِّري القسم الرابع المُعاد استخدامهما حرفياً)، PDF (عبر `lib/pdfExport.js` من جهة
  العميل، بنفس اختيار الأقسام 4-7 لتفادي مشاكل تشكيل الحروف العربية RTL في مكتبات PDF الخادمية)،
  و**Word حقيقي جديد كلياً** (`lib/pm/exporters/docx.js`، عبر حزمة `docx` الحقيقية المضافة إلى
  `package.json` - القسمان السادس والسابع وثّقا صراحة عدم وجود مُصدِّر Word في المنصة؛ أُضيف هنا
  فعلياً، ووُلِّد واختُبِر ملف .docx حقيقي بالعربية RTL خلال البناء وتأكَّد أنه صالح OOXML فعلياً).

### الذكاء الاصطناعي
نفس نمط `lib/equipment/ai.js` تماماً: استدعاء حقيقي لـAnthropic API (`lib/hse/ai.js`) عبر
`ANTHROPIC_API_KEY`، بلا هذا المتغيّر تعمل بقية القسم بشكل طبيعي تماماً مع رسالة خطأ واضحة
(`AI_NOT_CONFIGURED`). أربع دوال مبنية بالكامل على بيانات حقيقية من `hse_*` (لا بيانات وهمية تُغذّى
للنموذج): `analyzeSafetyPatterns` (اكتشاف الأنماط + الأسباب الجذرية المتكررة + توقّع المناطق
الأعلى خطورة معاً)، `suggestPreventiveActions`، `generateSafetyImprovementPlan` (تقييم أداء الفريق
+ خطة تحسين)، `summarizeSafetyReport`. **قيد إلزامي مُطبَّق حرفياً من البند 21**: لا دالة هنا تكتب
إلى قاعدة البيانات أو تستدعي `decidePermit`/`closeIncident`/`approveAndCloseCorrectiveAction` - كل
دالة للقراءة والتحليل فقط، تُعيد JSON لعرضه على مستخدم بشري يتخذ القرار، مع تنويه (`disclaimer`)
صريح في كل استجابة. "التنبيهات الاستباقية عند ارتفاع المخاطر" (المطلوبة في قائمة قدرات الذكاء
الاصطناعي بالوثيقة الأولى) مُنفَّذة كقواعد حتمية في `notificationsScan.js` بدل استدعاء نموذج لغوي
في كل طلب - أكثر اتساقاً وتعمل حتى بلا مفتاح API.

### الصلاحيات RBAC
امتداد إضافي فقط لـ`lib/pm/roles.js` المشترك - **دور جديد واحد فقط** (`hse_manager`/مدير
السلامة): كل الأدوار الأخرى المطلوبة في مواصفة القسم (مسؤول/مهندس السلامة، مدير المشروع، المهندس
المشرف، المشرف الميداني، العامل، المقاول، العميل) طابقت أدواراً موجودة أصلاً فوُسِّعت صفوفها
(`safety_officer`، `project_manager`، `engineer`، `supervisor`، `worker`، `contractor_rep`،
`client`) بدل تكرارها - ونفس منطق `equipment_manager`/`warehouse_keeper`/`procurement_officer`/
`quality_officer`/`projects_manager` امتدّ بصلاحيات محدودة حيث كان ذلك منطقياً فعلاً (رؤية فقط،
أو تقاطع تشغيلي حقيقي كمخزون PPE مع أمين المخزن). تسع وحدات صلاحية جديدة تجمع الجداول الخمسة
والعشرين حسب سير العمل (انظر التعليق التفصيلي في `lib/pm/roles.js`).

فروق واقعية مقصودة تستحق الذكر: **العامل يستطيع إنشاء بلاغ حادث/قريب من حادث** رغم محدودية بقية
صلاحياته - ثقافة إبلاغ بلا لوم، مبدأ سلامة معروف - لكن تعديل بلاغ غير بلاغه هو مرفوض في طبقة الـ
API لا في المصفوفة الخام (نفس أسلوب تقييد "عملياته فقط" للمُشغِّل في equipment_operation). اعتماد
تصاريح العمل النهائي محصور بـ`hse_manager`/`project_manager` - مسؤول السلامة نفسه يُعدِّل لكن لا
يعتمد نهائياً، تدرّج واقعي لأعمال عالية الخطورة كاللحام/الأماكن المغلقة. **هوية الفاعل تبقى بلا
نظام مصادقة حقيقي** (نفس القيد المُصرَّح به في كل قسم سابق) - الدور يُختار من `ActorBar` المشترك
ويُرسَل صراحة في كل طلب، وليس هوية مُتحقَّقة من جلسة دخول فعلية.

### الأمان
نفس ضمانات الأقسام 4-7 حرفياً: كل استعلام عبر `db.prepare()` بمعاملات مُجهَّزة (لا سلسلة SQL
مُركَّبة من مدخلات المستخدم مباشرة - حماية حقيقية من SQL Injection)، لا استخدام
`dangerouslySetInnerHTML` في أي مكوّن (حماية React الافتراضية من XSS تبقى فعّالة)، عمليات مركّبة
(إنشاء تصريح+ترقيمه، تسجيل نتيجة بند+إنشاء إجراء تصحيحي، توزيع PPE+خصم مخزون) داخل
`db.transaction()` حقيقية (atomicity فعلي)، فهارس (`CREATE INDEX`) على كل عمود يُستعلَم عنه بكثرة
(project_id، status، risk_level، expiry_date...). سجل تدقيق حقيقي (`hse_audit_log`) يسجّل before/
after JSON لكل عملية إنشاء/تعديل/اعتماد/حذف. **ما هو غير حقيقي بصراحة**: CSRF غير معالَج (يتطلب
نظام جلسات حقيقياً غير موجود في المنصة)، لا تشفير حقول حسّاسة عند السكون (encryption-at-rest) -
SQLite ملف عادي على القرص، لا نسخ احتياطي تلقائي مجدوَل (يتطلب مُجدوِلاً مستقلاً غير متاح في بيئة
Next.js API routes الخالصة هذه).

### الأداء
فهارس على أعمدة التصفية الشائعة عبر الجداول الخمسة والعشرين، `LIMIT`/`OFFSET` حقيقيان (pagination)
في كل دالة `list*`، لا استعلام "أحضر الكل ثم صفِّ في JavaScript" لأي جدول كبير محتمل (الحوادث/
التفتيش/الإجراءات التصحيحية). SQLite بوضع WAL (من `lib/db.js` المشترك) يدعم آلاف السجلات بسلاسة
لحجم شركة مقاولات واحدة - وهو نفس نطاق الأداء الواقعي الذي أقرّته الأقسام 4-7 عن نفسها (وليس نطاق
منصة SaaS متعددة المستأجرين بملايين السجلات).
